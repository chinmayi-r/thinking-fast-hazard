# Port preconditions: what each method assumes, and what HAZARD gives

The process CR set on Oct 16: before implementing any paper on HAZARD, list the conditions the paper's results rest on, compare each to what HAZARD actually provides, and say whether the match is direct, needs an adapter, or breaks. Nothing gets built until the mismatch column is read.

**What HAZARD provides** (from the repo docs and the paper note, [[zhouHAZARDChallengeEmbodied2024]]):
- ThreeDWorld, 30 FPS when a clock is imposed (RRARA's convention); the simulator steps only when the agent returns an action unless a time-conversion rule is added.
- Observations: RGB-D, segmentation, a temperature or water-level map, a semantic map, a goal map. Partial: you see what the camera sees.
- Actions: `walk_to(id)`, `pick_up(id)`, `drop`, `explore`, plus low-level Replicant moves. A high-level action takes many frames; the count is not documented and must be measured.
- Dynamics: fire spreads with a probability that rises over time; water rises; wind blows objects. Stochastic, continuous, not scheduled at fixed times.
- Outcomes: actions can fail (pickup of a burning object, blocked path). Durations vary with distance.
- Scoring: value of rescued objects, steps per rescue, damage rate. Deadlines are implicit: an object is lost when it burns, floats away, or blows away, at a time nobody announces.
- No simulator snapshot/restore API is documented; MCTS in the repo plans over an abstract internal model (inferred from the docs, to be verified in the code).
- Shipped agents: random, greedy, rule-based, PPO, MCTS, LLM v1/v2. PPO training infrastructure exists.

| Method | What it assumes | HAZARD match | What a port would need |
|---|---|---|---|
| **Coles 2024** (planning line, most recent) | A symbolic PDDL model with durative actions and *known* durations; deadlines as timed initial literals at *known* absolute times; deterministic action outcomes; a forward-search planner (OPTIC) with a temporal network per node; time counted as node expansions; estimates of remaining search time from expansion delay and heuristic error | Breaks on four counts: no symbolic model exists; deadlines (burn times) are unknown and stochastic; outcomes fail; time is frames, not expansions | Write a symbolic abstraction of a HAZARD scene (objects, values, rooms, estimated time-to-loss per object as a *distribution*, which is Shperberg's setting, not Coles's); replace OPTIC with a small planner over subgoal sequences; map expansions-per-second to wall-clock. What survives intact: the dispatch rule's shape, act now if P(success|act) beats P(success|wait) by a margin, and the restriction of further search to branches consistent with the dispatched action. Verdict: a *Coles-shaped* baseline, not Coles |
| **Shperberg 2021** (planning line) | Several candidate branches with known distributions over compute needed and over deadline; one processor; independence; plan complete before acting | Partial: candidate subgoals (which object to rescue next) are branches; deadline distributions can be estimated from temperature or water level; compute profiles can be measured (LLM latency distribution) | A deadline-aware subgoal scheduler: score each candidate rescue by DDA's "utility per unit minus utility lost by delay," using measured LLM latency as the profile and estimated time-to-loss as the deadline. Drop "plan complete before acting." Verdict: portable as a scoring rule; the planner itself is not |
| **Muppidi 2026** (RL line, most recent) | Discrete frames at fixed rate; a *perfect simulator* for committed-action rollouts; a pretrained AlphaZero planner (policy and value nets) for the environment; reflex = that net without search; a small discrete budget set; full observability; many cheap episodes for PPO | Frames yes. Perfect simulator no (no snapshot API; 3D sim is slow). AlphaZero planner no. Full observability no. Cheap episodes no | Replace "MCTS with k simulations" by "LLM or planner call that takes k frames," reflex by the repo's rule-based agent (as RRARA does), and the gate by a small network over features (nearest-hazard distance, target distance, time since last plan). Train the gate with the repo's PPO scaffolding. Verdict: the *idea* ports (learned budget with a reflex fallback); the method does not. Note it then equals RRARA plus a learned switch |
| **Ramstedt 2019** (RL line) | One fixed timestep of delay; state augmented with the action in flight; off-policy actor-critic on continuous control | Direct for the state construction; the one-step delay is a special case of TCM | Include "action currently executing" in any gate's input. Verdict: a design rule, not a baseline |
| **Travnik 2018** (RL line) | Act before the learning update; tabular or tile-coded SARSA; single-core | Direct in spirit (act before slow computation finishes) | This is RRARA's reflex-first ordering. Verdict: already present in RRARA |
| **Sleep-time Compute 2025** (Tom's list) | Context available before the query; preparation is text rewriting by an LLM; amortization across queries on one context | Partial: the scene layout and object list are known before the hazard starts; RRARA's PrePlanner cache and A* precompute are preparation in kind | Define X as "work done on the scene before the hazard starts" (precompute paths, object values, candidate rescue orders, or train the reflex on this scene family) and vary its amount. Verdict: the X axis is implementable; the method (text rewriting) is not the point |
| **Moerland 2020** (Tom's list) | An AlphaZero plan-learn-act loop with a fixed total compute budget | No AlphaZero loop on HAZARD | Only as the question "how to split a training budget," if a learned gate is trained. Verdict: not a baseline |
| **Russell & Wefald 1991** (Tom's list) | Estimated utilities of actions; an estimate of how a computation would change them; a time cost | Direct as a rule: compute if E[gain] − time cost > 0 | Hand-derived version of the gate, with E[gain] from the reflex's uncertainty and time cost from measured latency × hazard spread rate. Verdict: the simplest non-learned gate baseline; Coles is its planning-side instantiation |
| **RRARA 2025** (third strand) | HAZARD itself; 30 FPS; blocking inference; a rule-based reflex; an LLM reflector; staleness weights (unpublished) | Direct, it was built here | Reimplement from the paper; the staleness weights must be guessed and flagged. Verdict: the natural first non-trivial baseline, and the Karthik "fast acts at n, slow reasons about n+1" idea in existing form |
| **When to Plan 2026** (camp 4) | Reactive ensemble behaviour-cloned from planner rollouts; A* at fixed depths; world static while planning; planning cost −αk in reward; hand-designed meta-features | Breaks on the static world; A* over what? | Learned switch between reflex and LLM/planner with the world moving (TCM) and the meta-features (ensemble disagreement, history). Verdict: the learned-switch idea ports; combined with RRARA's protocol it is the gate Tom wants |

**Tom's own order (Oct 1 transcript):** first see if the benchmark runs; second take a baseline from one of the prior works; third, his weak baseline, ask Claude or Codex to solve the environment directly and watch it fail because of thinking time; then the research idea, the fast-LLM-acts-now, slow-LLM-reasons-ahead reconciliation, which he called "more direct" than true anytime. RRARA is that idea with a rule instead of a second LLM.
